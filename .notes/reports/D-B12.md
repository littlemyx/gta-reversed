## Hand fixes found by the compile / review
* Detached `NOTSA_GLOBAL_DEF` emits the type at namespace scope: `CPool<CVehicleStructure>*` (nested class) and `CObjectData[NUM_OBJECT_INFOS]` (class constant) must be written fully qualified (8299903e). The codemod does not qualify them (worth a tool fix for later batches: qualify names found in the class scope when emitting DEF).
* `extern tRestoreEntry (&gRestoreEntries)[N]`: `NOTSA_GLOBAL_EXTERN` cannot spell an array reference; same `#ifdef NOTSA_GLOBALS_DETACHED` pair as AEAudioEnvironment.h, with a `#line` to keep `__LINE__` (8299903e).
* Stray found by `--check-converted` after B13: `ProcObjectDebugModule.cpp` (toolsmenu) edits `CPlantMgr::Update()`'s two function-local statics through `(int8*)0xC09171/0xC09170`. Not nameable from outside the function: the two ImGui lines are now `#ifndef NOTSA_GLOBALS_DETACHED` (+ `#line`), address mode text/line numbers unchanged (7dfbab88).

## SIN_LUT (Maths.cpp 0xBB3E00 + two WaterLevel.cpp aliases): proposal of D-B09.md held up, implemented
* `Base.h` (own commit 34a18fdf, before anything else): `NOTSA_GLOBAL_INIT(name, addr, (T), expr)`. Address mode: `const auto& name = StaticRef<T>(addr) = expr` (exactly the old text, internal linkage); detached: `T name = expr` (external linkage) + the usual verify registration.
* Maths.cpp: owner via `NOTSA_GLOBAL_INIT(SIN_LUT, 0xBB3E00, (std::array<float, SIN_LUT_SIZE>), []() {..}())`. WaterLevel.cpp: `NOTSA_GLOBAL_EXTERN(SIN_LUT, (std::array<float, 256>));` on the former blank line 6 (no `__LINE__` shift) + `static NOTSA_GLOBAL_ALIAS(SIN_LUT, 0xBB3E00, (..), ::SIN_LUT);` for the two locals (address mode: the old `static auto& SIN_LUT = StaticRef<..>(0xBB3E00)`). The `extern T& SIN_LUT` of address mode is never odr-used (no symbol, no code).
* `standalone_deviations.tsv`: `0xBB3E00 0 0` (the image holds zeros, the exe fills the table in InitMathsTables after the snapshot; the detached build fills it at static init with the same x87 sequence) -> 1024-byte global, deviation bytes 40 -> 1056 in verify (bytes that are 0 in both do not count). `codemod_globals.py` knows the macro (MACRO_ADDR_ARGS / OWNER_MACROS, 2 lines) so `--check-converted` counts it as an owner (ad39b1f1).

### The one failed poison run (`soak_tip`, first run on this exe)
`RESULT: FAIL`: 16 markers (last `cheat_rhino`), access violation at `CFileLoader::LoadObjectInstance:1225` <- `CIplStore::LoadIpl` <- `CStreaming::ConvertBufferToObject` while the Rhino was spawned. Registers: EAX = 0 (null `new CDummyObject()` result), EDX = 2500 = the dummy pool size, ECX = 0x701: the dummy pool (`CPools::ms_pDummyPool`, 2500 entries) was full when a streamed IPL asked for another dummy, `CDummyObject::operator new` returned null and the next virtual call dereferenced it. Not reproduced in 3 further runs of the same exe and route (poison tip2, no-poison np, census), so it is a flake; none of the registers/addresses point into a converted range (the CStore objects are address-mode, ms_modelInfoPtrs is not involved), no stray read was logged. Likely a pre-existing streaming/IPL-removal timing issue under host load (other agents' builds and WIN-PERF fps runs were active); worth a look by whoever owns CIplStore/pools (the vanilla game never fills the dummy pool, so some IPL unload path probably leaked dummies).
