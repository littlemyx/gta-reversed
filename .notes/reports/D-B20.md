## 2. Static-init order

### Audit (D-C12 / C34 / C56 reports + the dynamic-initialiser list of the link map: 181 distinct objects with a `??__E` initialiser besides the registrars)
Cross-object effects of the exe's / the repo's static constructors, and why none depends on the link order:

| writer (dynamic init) | touches | why order does not matter |
|---|---|---|
| `FrontEndMenuManager` (CMenuManager ctor, exe 0x574350, 52 B in 25 ranges) | `g_fx`+0x54 (FX_QUALITY_HIGH = 2) | `g_fx` is `{}` of a trivial class = constant-initialised storage (not in the link map's initialiser list), so it exists before ANY dynamic initialiser; the ctor's store always lands after |
| same | `AERadioTrackManager` +4/+7 (`m_bBassEnhance`, `m_bRadioAutoSelect`) | both flags are part of AERadioTrackManager's own initial value (D-C56): the result is the same whichever of the two runs first |
| same | `CCamera::m_fMouseAccelHorzntl`, `m_bUseMouse3rdPerson`, CVehicle mouse flags, `CRenderer::ms_lodDistScale` | constant-initialised statics whose initial value equals what the ctor stores |
| `TheCamera` ctor chain (`CCam::Init` x3) | `gIdleCam.Reset(true)` and the constant-initialised camera globals; `CPad::GetPad()->LastTimeTouched = CTimer::GetTimeInMS()` | every writer stores the same bytes as the other side's own init (gIdleCam / CTimer constant-init; `CPad()` sets `LastTimeTouched = 0` and the timer is 0 at that time) |
| `gHandShaker`, menu station (rand) | rand state | the 18 + 1 draws are literals now (`MakeExeHandShakers`, station pinned to 2): no rand() in static init |
| `CPedGroups::ms_groups` | addresses of `CPedGroupDefaultTaskAllocators::ms_*` | address only (fixed storage), no read |
| header `inline` globals | hoisting | with the PCH every TU "defines" every PCH inline variable, MSVC initialises all of them at the first object of the link line that contains them (PCH object = 2nd after the pad object): their relative order is the PCH's declaration order in every link order; only their order relative to .cpp-level objects moves with the link |
| **`CMissionCleanup::Init`** | **found by this slice**: `m_Objects.fill(tMissionCleanupEntity())` copies a temporary whose 3 padding bytes per element are uninitialised stack bytes | the end state of `MissionCleanUp` (150 bytes) was zero by luck in CMake's order and garbage after reversing the object order -> in-place assignment in the detached build |

No `#pragma init_seg` (rejected in D-C56: it also moves the COMDAT initialisers of inline variables defined in the same TU). The mechanism is: **constant initialisation for everything a ctor writes into, initial values that already contain the cross-ctor stores, no cross-object reads** - plus a regression test that would catch a new dependency:

### Proof / regression tooling
* `tools/standalone/initorder_link.py`: relinks the detached exe from the already built objects with another object order (`--mode reverse | shuffle --seed N | rotate | none`, the data-image pad object stays first), no recompile (~2.5 min); `--compare REF DUMP` diffs two boot dumps byte for byte except pointer-like dwords (which move with the layout, 15,387 of them).
* `NOTSA_POISON_STACK=1` (verify builds, `GlobalsVerify.cpp`): at `.CRT$XCB` the exe takes over the rest of the CRT's `_initterm` table, nulls each entry and calls it itself with the 256 KB below the call filled with 0xCD, so an uninitialised read in ANY static constructor shows up as 0xCD in the boot dump in any link order. Mutation test (old `Init()` put back): `MISMATCH MissionCleanUp ... 225 bytes differ, ours cdcdcd0000...` with the variable, PASS without it (= the bug was invisible in the normal order). My first variants did nothing: a normal function filling the stack leaves its own frame unpoisoned exactly where the next initialiser's frame starts, and a poison pass that runs only once at the start is overwritten by the first initialisers that reuse the same stack depth (the previous initialiser's leftovers are what the next one reads); hence one fill per call. A stand-alone test (`C:/gta-scratch/b20/t/t12.cpp`) isolated both effects.

## 5. Notes
* Lessons: (1) `#line N` after a hand edit needs the LOGICAL number of the next line: `sed -n` / `grep -n` print physical numbers, which differ in every file that already has an earlier `#line`. (2) The codemod's cast alias for array types (`reinterpret_cast<T[N]*>`) is invalid C++: `T(*)[N]`. (3) Heredocs passed to the shell tool interpret `\\`/`\n` (again): macros with line continuations were edited with the Edit tool. (4) A static-init padding bug is invisible with a quiet stack: always run the boot dump once with `NOTSA_POISON_STACK=1`.
* `LNK1201: error writing to program database` on the shared Detached link (3 times in a row, mspdbsrv not killable by me): renaming `bin/gta_reversed.pdb` (my own artifact, kept as `.old_b20`, 200 MB, deletable) made the next link succeed.
* The MissionCleanup fix is detached-only (`#ifdef NOTSA_GLOBALS_DETACHED`): the DLL build keeps the original `fill()`, whose padding bytes are never read.
* Scratch: `C:/gta-scratch/b20` (scripts `io_run.sh` / `io_all*.sh` / `fin.sh` / `mut2.sh`, `dump_*.sh`, stash dirs, stand-alone poison tests in `t/`), `C:/gta-soak-out/b20` (all dumps, verify / vptr / compare outputs, soak_f, census_f), `C:/gta-census-b20-out`. The `io_*` relink dirs (458 MB each) are deleted.
