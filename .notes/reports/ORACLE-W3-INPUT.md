## Observed, not changed
- `WinInput::GetMouseSetUp` (0x53F2D0) takes the result pointer on the stack with `ret 4` in the exe (a trailing bool stays on the stack as the second argument of InitDefaultControlConfigMouse, `ret 8`); the port returns the struct by value with the cdecl convention. No exe caller is left in the port; WinInput is not part of this target.
- Port asserts / NOTSA_UNREACHABLE for inputs the exe tolerates: GetIsMouseButton* with a key above 7, GetIsKeyBlank / GetControllerState with a type above 3, GetControllerStateJoyStick with a button above 16, CheckMouseButton. The rows use the value sets the game produces.
- IsKeyboardKeyDownInState: the exe compares the key as a signed int (`key < 0xFF`), the port unsigned; keys come from a table of values below 0x10000, rows use those.
- `CPad::iCurrHornHistory` outside 0..4 (exe: unsigned compare after the increment, port: `% 5`); the game keeps it in range, rows use 0..4.

## hang (INPUT-HANG, 2026-10-20 09:45 - ~11:00, rules v3)
The orchestrator's gate saw `wave3_input_oracle_test` "hang" 3 times in 15 min at different rows (logs C:/gta-scratch/run_all_tests.116581/wave3_input_oracle_test.{1,2,3}.log). **It was not a hang: the target needed ~18 min, run_all_tests kills an `*oracle*` target after 900 s** (TMO in run_all_tests.sh). The ORACLE-W3-INPUT worktree run was started by hand without that limit.
- Evidence: full run in a fresh worktree on origin acb54935, W2_PROGRESS=1 with a per-line timestamp (C:/gta-scratch/inhang/run1.log): every row advances (6000 cases = PC24 + PC53, 5-31 s per row), `ButtonDown_VehicleAndThirdPersonOnly` finishes at 941 s, last row at 1095 s, exit 0, PC24 0. Attempts 1 and 2 of the gate stopped right after that row (900 s), attempt 3 earlier (37 rows) because the machine was busier. No row reads OS input (checked: no GetAsyncKeyState / DirectInput / SDL call is reachable from the rows; the exe side is patched with host stubs), no uninitialised loop bound; stack samples with cdb (12, then 2 x 20) always showed the same few frames, never a stuck one.
- Why a case costs 5 ms: the targets are `/Od /Ob0 /RTC1` and per case the harness (a) compares the 4 MB data image with the CRT `memcmp` (a call per dword, `unaligned_memcmp` / `cmpDWORD`, 11 of 12 samples) and, after that is fast, (b) fills the 128 KB scratch block with `FillGarbage` (~half of a case), (c) copies the image three times.
- Fix (harness only, no port change): `tests/standalone/oracle_fast.cpp` (own TU, `#pragma optimize` + `runtime_checks off`, macros instead of /Ob0-blocked member functions): SSE2 `BytesDiffer`, a bit-identical `FillGarbage` (start-up self-test against the /Od reference: bytes, Rng state, g_special; abort on a difference), and a delta snapshot of the image (changed 64-byte blocks instead of a second 4 MB copy; on a difference the port-side image is rebuilt and the old report path runs). Opt-in with `ORACLE_FAST_HELPERS` (CMake: wave3_input_oracle_test only; every other target keeps `memcmp` and the /Od code). `kScSize` 0x20000 -> 0xC000 (the highest fixture ends at 0xB000). Default case counts of the rows halved (`W3I_DIV` default 2 instead of 1; `W3I_DIV=1` = the previous counts, 119 s; the pre-fix failure counts in the table above were measured at half counts, so detection power is as validated).
- Mutation check of the delta compare: a stray image write added to the port's GetIsKeyBlank is reported (`r1 m+2CB900 got 01 exe 00`, PC24 578/1500), the port restored afterwards.
- Result: one run 58 s sequential (was 1097 s); 20 runs (4 batches x 5 in parallel, so slower than alone) each 95-98 s, exit 0, 67 functions, PC24 0 / PC53 0 every time (C:/gta-scratch/inhang/results.tsv). `wave3_ui_oracle_test` and `wave3_camera_oracle_test` still build with the shared-header edit (their behaviour is unchanged: `BytesDiffer` is `memcmp != 0` there, FillGarbage the old code).
- Side finding: `run_all_tests.sh` kills a hung target with `taskkill //F //IM <test>.exe` (all processes of that name on the PC). My first timing run of the same exe name died with exit 1 the second the orchestrator's gate started; use a copy under another name when running a target beside a gate.
