## Static-init order (plan R2)
All C1/C2 objects are inline statics / namespace globals with dynamic initialisation (unordered across TUs), so the rule is "no ctor may read another dynamically initialised object". Checked by reading every ctor:
* `CColModel()`, `CCollisionData()`, `CMatrix::SetScale`, `CMatrixLinkList()` (`m_pObjects = nullptr`, no `Init`), `COctTreeBase()`, `CGangInfo`, `CInformFriendsEvent` / `CInformGroupEvent`, `CPedScriptedTaskRecordData`, `CScriptedBrainTaskEntry`, `CInterestingEvents()`, `CTaskComplexSequence()` (-> `CTask`), the allocator vptr: write only their own members, no pool / heap / other global.
* `CPedGroup()` -> `CPedGroupIntelligence(this)` takes `&CPedGroupDefaultTaskAllocators::Get(STAND_STILL)` = the ADDRESS of `ms_StandStillAllocator` (fixed storage), and `CPedGroupMembership(group)` the address of its owner: order independent. The pointer values are checked in 2b.
* `ms_offsets`, `gDummyMatrix` ({ `CMatrix::Identity()` }) are self-contained initialisers.
* No other converted global (C3-C6 objects) names a C1/C2 object in its ctor (CColModel members of CVehicle / the camera are plain members). The boot log has no early-use crash, and the poison run would turn an uninitialised read into 0xDD garbage.
The exe's `_initterm` order also registered `atexit` for the same destructors (plan section 2.3: "20 atexit-only"), so exit-time behaviour matches.
