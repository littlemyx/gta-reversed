# RR resource load order and streaming behaviour (SH2, from a logged run)  - committed as .notes/STATEHASH_LOADORDER.md

Source: `NOTSA_SH_LOADLOG=<file>` (source/portable/loadlog.h; hooks: CFileMgr::OpenFile, CStreaming::LoadCdDirectory / RequestModel / ConvertBufferToObject / RemoveModel / Update, CdStreamRead). Full log of the reference run: `C:/gta-scratch/statehash/ryder1/record.load`
(925156 rows, 50 MB, mostly `STREAMING_UPDATE` markers and `REQ ... state=1` repeats). Filtered log (all FILE / IMGDIR / CDREAD / CONVERT / REMOVE rows + REQ rows of models that were NOT loaded): `C:/gta-scratch/statehash/ryder1/loadorder.txt` (11797 rows, the list to compare with).
Row: `seq fc=<CTimer frame counter> rec=<recorded frame or -1> KIND args`. KINDs: `FILE path mode` (every CFileMgr::OpenFile, in call order), `IMGDIR file img=n`, `REQ id= flags= state=` (CStreaming::RequestModel at a state NOT_LOADED(0) or LOADED(1)),
`CDREAD stream file sector count` (the read of one streaming request, performed synchronously inside the call), `CONVERT id= size=` (ConvertBufferToObject: the moment the loaded data becomes the model / txd / anim block / collision object that entities can use), `REMOVE id= state=`, `STREAMING_UPDATE` (start of CStreaming::Update).

## Order (pre-record = everything before `rr_start`, 224 FILE rows, 5 IMGDIR rows)
* Files are opened by the game's own loaders in the exe order (no reordering in RR mode): gta_sa.set, models/coll/peds.col, data/fonts.dat, ... (see the first 224 `FILE` rows of loadorder.txt; they include the IDE / IPL / DAT / ped.dat / handling / timecyc / popcycle / audio config files in gta.dat order, `AUDIO\STREAMS\...`, `sa-utrax.dat`).
* At fc=289 the IMG directories are read: `MODELS\GTA3.IMG` (img 0), `MODELS\GTA_INT.IMG` (1), `DATA\PATHS\CARREC.IMG` (2) + 2 more; directory entries are looked up by name against the model infos registered by the IDE files (so the streaming id of a resource is fixed by the IDE/TXD/IFP registration order, not by the IMG order).
* Then the boot requests (ids 25001.., `REQ ... state=0`), each followed by its `CDREAD` and `CONVERT` (loading screen / new game load use `LoadAllRequestedModels`: every request completes before the call returns, in request order, priority requests first).
* Mission start (rec=1..2): `REQ id=1277`, `CDREAD`, then `FILE data\script\main.scm` (the mission script is read again from the file at the injected `mission:24`).
Counts: pre-record 681 CDREAD / 1409 CONVERT / 888 REMOVE; recorded frames 0..25906: 706 CDREAD / 1013 CONVERT (in 401 distinct frames) / 2503 REMOVE / 13 FILE.

## When do streaming requests complete (RR mode)
1. `NOTSA_RR=1` makes CdStream synchronous: `CdStreamRead` performs the file read inside the call that issues it (CStreaming::RequestModelStream / RequestFilesInChannel), so the BYTES are in the buffer when the request is issued - no thread, no wall-clock dependence.
2. The object is NOT created at request time. `ConvertBufferToObject` runs when the streaming channel is processed: inside `CStreaming::Update` (called first in every `CGame::Process`, before the rest of the simulation) or inside a blocking `CStreaming::LoadAllRequestedModels` / `LoadScene` / `LoadSceneCollision` (loading screens, `mdped` warps, `mission` start, vehicle/ped creation by scripts that wait for the model).
   Measured on the recorded frames (1013 REQ->CONVERT pairs): same recorded frame 388, +1 frame 133, +2 66, +3 41, +4 34, +5 24, +6 31, +7 28, rest later (a model requested in frame k can become usable up to several frames later, depending on channel occupancy: 2 channels, one request in flight per channel, the next one is issued after the previous conversion).
3. A model is therefore "loaded" at a frame boundary that is a function of the game's own calls only (request order, streaming list order, channel state), not of timing; the virtual clock does not time-slice streaming.

## Differences to the TS port as described to me ("streams synchronously at the end of each frame, 20 ms per frame, main.ts frame order") - please check each against main.ts
1. Position in the frame: ours = START of CGame::Process (CStreaming::Update first, right after CPad::UpdatePads); TS = END of each frame. A model converted by frame k's Update is visible to everything simulated later in frame k and to the frame-k hash (OnFrame runs after Process).
2. Completion model: ours = read synchronous, conversion through the 2-channel state machine (usually the same frame, sometimes up to 7+ frames later); TS (as described) = request completes synchronously at the frame end. If TS converts everything it requested in the same Update, the frame at which entities see a model differs for ~60% of the model loads (the +1..+7 rows above).
3. Blocking loads (LoadAllRequestedModels at loading screens, LoadScene in `mdped`, mission start) complete everything inside the call in both models; ours converts in request order with priority requests first.
4. Frame time: 20 ms virtual per Idle frame in ours, including loading and menu frames; CTimer frame counter at recorded frame 0 is 963 (0 at process start): CStreaming::Update's `fc % 128` tests (boats at 106) and the load monitor see that frame counter.
5. REMOVE (eviction) is driven by CStreaming::MakeSpaceFor / RemoveLeastUsedModel with the memory budget `stmem`: the pop hash field `stmem` (CStreaming::ms_memoryUsedBytes) at frame 0 is 0x24f1800.
Pool slot allocation order (the `slot` word of the pd / vh / ob hashes) follows the creation order, which follows this load order: compare `CONVERT` / entity-creation order first when a slot differs.
