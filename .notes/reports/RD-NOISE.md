Cause: `CCarCtrl::GenerateRandomCars` (0x4341C0). asm 0x434239..0x434261: `al=[0x9690C0]; test; je -> 2x GenerateOneRandomCar; dec al; mov [0x9690C0],al; jne skip; else 100x GenerateOneRandomCar`:
the 100-car burst happens only in the frame the start countdown **reaches zero** (2nd frame, once). The port ran the burst on every decrement (frames 1 AND 2). Proof from the D probe line (`D fc run cd cars.. perc..`, pin 64, both exes):
cd=2 at tick 0 and cd=1 at tick 1 in BOTH exes, PopCycle car counts identical (40c99999,3ee66669,40100000,00000000) - the exe's frame-1 generator calls returned without reaching ChooseModel, the port's did.
Second finding in the same function: the exe's tail 0x43426D was **missing in the port**: `CTrain::DoTrainGenerationAndRemoval(); CPlane::DoPlaneGenerationAndRemoval(); if ((prevMs ^ ms) & 0xFFFFF000) GenerateEmergencyServicesCar();` - nothing else
calls them, so the standalone never generated trains, planes or emergency-services cars (a gameplay bug, found only through the rand count).
Fix: commit 9ac69102 (CarCtrl.cpp). After it: frame 1 ncalls 74 = 74 and the RNG seed after frames 1 and 2 is bit-identical; A-B now first differs in the script-space hash at frame 1
(scr 45c1d448 vs 89cc797c - not investigated, lead for RD-FIRSTDIFF) and in rng/ncalls at frame 3 (189 vs 163).
Oracle row: not possible (the function drives the whole world: trains, planes, pools). Regression evidence = the lockstep frame-1 count (74 = 74) plus the asm above.
