# Standalone build: deliberate deviations from the original exe

Collected from `.notes/PHASE2_STATUS.md` (row in brackets). "Unobservable" = no effect on game behaviour that we could find.

## Game logic
* Where the exe reads an uninitialised stack value, we return a defined one (0/false): `CCollision::ProcessSphereTriangle` with `numPassed==0`, `ProcessLineBox` with `t0>1` [P2E, S2 CCollision].
* **Every `notsa::bugfixes::*` switch is OFF in the run build** (FIX-AUDIT, `.notes/reports/FIX-AUDIT.md`): `ReversibleBugFix::Enabled` defaults to `detail::kDefaultEnabled`, which is `false` under `NOTSA_STANDALONE_RUN`
  (the DLL/ASI build keeps the upstream default ON, object code unchanged). Before the audit all 17 fixes were ON in the run build, i.e. 37 call sites deviated from the exe: plate characters A-Z/0-9 instead of A-W/0-8,
  the rear-right light status, framerate-independent audio fades / map zoom (`pow(step, timestep)` instead of the exe's constant step), the stray road-switch areas of `SwitchRoadsOffInArea`, `RemoveDistantCars`'s remove-before-iterate order, the climb settle-speed clamp,
  the collision-audio / formation / pad-less null and OOB guards, and `CPool` destructors at pool shutdown (the one that crashed, BUG-REFS). They stay compiled and can be re-enabled one by one with `.Enabled = true` in `Bugs.hpp`.
* **Kept deviation** (needed for the port to run): the unconditional upstream default `wheelSizeFront/Rear = 0.7f` in the vehicles.ide line parser (`FileLoader.cpp`: the exe reads uninitialised stack when the line has fewer fields; the value depends on the Windows version, upstream NOTSA/BUG note) [FIX-AUDIT]. The former second one, `m_Mat.Detach()` in `C3dMarker::DeleteMarkerObject`, is gone: `C3dMarkers::Init` is ported from the asm and resets the markers field by field without touching the matrix like the exe [NOTSA-AUDIT].
* **NOTSA-AUDIT** (`.notes/reports/NOTSA-AUDIT.md`): upstream NOTSA changes that differ from the exe are taken out of the run build with `NOTSA_EXE_OR(exe, upstream)` / `#ifdef NOTSA_STANDALONE_RUN` (the DLL build keeps upstream's code, object code identical): no `RenderDebugShit()` in `Render2dStuff`; shadow `drawOnBuildings` flags (no FX-quality-very-high extension, ped/vehicle/real-time shadows as in the exe); light-shadow speed test `>`; corrupted-slot state not stored; `Clone()` of 4 tasks with a broken copy constructor and 9 tasks that used the memberwise copy now builds a fresh task from the arguments like the exe; `CFire::ProcessFire` and 41+ pool loops iterate backwards like the exe; REPLAY text blinks by frame counter; photograph range test (sqrt, objects no longer inverted); `OurPedCanSeeThisEntity` distance by sqrt; Mayhem cheat without the acquaintance-table swap / OFF branch; gang territory zone classification, ranking order and `GangRatings[rank] = gang`; camera pickup coronas share one id; corona reflection ground-height refresh every 16th frame per corona; `ResetIP` leaves the IP stack.
* `FIX_BUGS` is off in the run build; remaining `IsFixBugs()` guards (e.g. null guards when a pool is full, `CTaskSimpleBeHitWhileMoving::StartAnim` null anim) are inactive, so the exe's behaviour is kept [D7/D8, S1 phase 1e].
* Run-build guards where the exe relies on UB: `CAutomobile::ProcessEntityCollision` null colmodel, `CCover::Update` stale buildings, CRT "array subscript out of range" report tolerated (the exe reads the neighbour) [S5-librw update 3].
* `CWorld::FindPlayerSlotWithVehiclePointer` 0x564000 returns 0 in the exe, port returns -1; `GangLeader::ControlSubTask` keeps nullptr where the exe would `_purecall` [S1 D10-D12, S2 hooks].
* `NOTSA_DEBUG` not defined: no siren cheat Ctrl+J/K, no SoundManager stack-trace module, no Replay iterator asserts; UIRenderer (ImGui, F7, debug hotkeys, `RHManager::CheckAll`) is stubbed [D7/D8].
* `NDEBUG`: the original has no asserts (e.g. `CRect` flip in `DoFade`) [S5 2026-10-10].
* Debug-only extras kept as is, inert for valid data: `_DEBUG` bounds check in `Population.cpp`, `Pool.h` `NOTSA_DEBUG_BREAK`, memory logging [D7/D8].
* `Population.h` fields behind commands 2435/2462 look swapped (byte semantics kept) [S6-I]; open TODO: 2463 `-1` path allocates with plain `new` instead of the task pool [S6-I].
* Script commands: `GET_HASH_KEY` in the exe reads an uninitialised stack label (oracle zeroes the stack) [D-REL].
* `Idle()` (0x53E920) frame lock: the exe busy-waits until >= 14 ms (unsigned ms from `CTimer::GetCurrentTimeInCycles()/GetCyclesPerMillisecond()` vs `g_LastTickTime` 0xB72CA8) have passed since the previous `Idle`, regardless of the frame limiter. Upstream NOTSA had it commented out; it is now ported verbatim and always on, in the standalone AND the DLL build (the DLL build's `Idle` replaces the exe's, which has the lock). Without it the port ran at 270-2000 fps and the new-game intro stalled. Not a deviation any more; recorded because the old behaviour differed [IDLE-LOCK, `.notes/reports/IDLE-LOCK.md`].
* Detached boot state (stream D phase C5/C6): `FrontEndMenuManager.m_nRadioStation` and `gHandShaker[].m_vel` are rand-derived in the exe (the static ctors draw 19 values from a seed-1 CRT, deterministic); the run build reproduces them exactly (the station is pinned to 2, the 18 handshaker values are committed bit patterns) instead of drawing in its own static-init order, so no deviation row is needed. `CMenuManager`'s ctor now matches the exe where the port had slipped (`m_bShowSubtitles` default false, map origin y = 224). Audio entities / managers that are globals start all-zero like the exe's .bss (the repo's `-1` / `true` member defaults only apply to heap / stack objects) [D-C56, `.notes/reports/D-C56.md`].

## RenderWare shim (librw-based)
* **MANAGED vertex buffers** instead of the exe's shared pools (behaviour-neutral); no morph-target interpolation, no LRU instance arena, no NATIVE geometry [P2B-07].
* **`renderFrame` is never incremented** (as in the exe: `RpWorldRender` has no callers); the car env-map once-per-frame guard therefore never fires [fidelity leftovers].
* **PAL8 textures are expanded at load** to 32 bit (only `outro.txd` has PAL8); `RwRasterLockPalette` returns NULL for them; `RwRasterCreate` with P8 on an open device returns NULL [P2B-03a/b].
* **Bump map not ported** (one material in `gta3.img`, `tikitorch01_lvs`); the D3D9 light-setup/pipeline table-sqrt sites at 0x814F0D.., 0x755193, 0x76500B are bump/tangent code, unused [MatFX pipeline, fix4].
* **Light slot order** differs from the exe's; invisible after 8-bit quantisation, not implemented [fix4].
* **Sub-hierarchies** and UV key-frame Blend/Add/MulRecip are not implemented (the game never calls them) [P2B-05b]. `RpLightGet/SetConeAngle` are ported but unused by the game [fix4].
* `D3DCREATE_PUREDEVICE` is not added (librw does not query caps first); `D3DCREATE_MULTITHREADED` is correctly not set (the exe never writes it) [librw fork patches, D7].
* `_rwD3D9EnableClippingIfNeeded` is the exe's verbatim loop (NaN counts as inside, negative radius differs from librw) [librw fork patches].
* `_rwStreamInitialize` ignores the caller-supplied storage (heap stream); `RwFree` is a thin wrapper; `RwStreamClose` on stale streams is an open issue [P2B-01, S5].
* `SetMaterial` cache invalidation differs from the exe (deliberate); `ALPHATESTENABLE` tie to blending is unverified [P2B-02c].
* librw fork patches change behaviour to match SA (anisotropic filtering, `sortLikeSA`, case-sensitive UV-anim lookup, matrix kernel order); a texture dictionary iterates newest first as in the exe [P2B-03b, fork].
* Textures: the exe-checked pixel/format decisions (BMP reader is our own because librw pads rows wrongly; camera-texture lock is own code) [P2B-03a].
* Skin pipeline: until the vs_1_1 / CPU path lands, librw's skinning is used instead of the exe's shader/CPU skinning [11x-4, S3 skin row].
* MatFX: stages >= 1 disabled explicitly, pixel shader cleared after the draw, PS constant written after `flushCache` (librw clobbers c0) [MatFX AllInOne].
* Im2D/Im3D: the exe's FF driver is ported, the textured stage-0 branch is untested [P2B-06].
* RW maths: remaining small `RwSqrt` table gaps in ConvertFromMatrix/SetupSlerpCache/Blend/Rotate and `BoneNode_c::BlendKeyframe` early-outs (NaN only) [11x-4].
* Wine only: restore callback via a device-vtable `Reset` proxy, real `D3DERR_DEVICELOST` path untested; DEC3N vertex path untested [P2B-09, P2B-07].

## Platform
* No DirectShow: videos are skipped (`NOTSA_STANDALONE_SKIP_VIDEOS`); no 800x600 mode on Wine, first mode with width >= 800 is used [S5-librw].
* `NOTSA_STANDALONE_MUTE=1` (env, off by default): DirectSound secondary buffers get a patched vtable whose `SetVolume` only ever sets `DSBVOLUME_MIN` on the real buffer while `GetVolume` returns the volume the game set (audio logic unchanged, output silent); no effect without the env var [MUTE].
* `NOTSA_STANDALONE_WINDOWED=<W>x<H>` (env, off by default; `soak.sh`/`census.py` set 960x600 on the Windows host): windowed D3D9 device (back buffer = window client area, no desktop mode change, captioned non-topmost window shown without focus) instead of exclusive fullscreen; a synthetic W x H mode is appended to the video mode list and selected over the saved/default mode, every exclusive mode is windowed inside the device layer but still reported as exclusive to the game (same `fullScreen`/`RsGlobal` sizes/HUD scale). Present goes through DWM (no exclusive flip chain), so frame pacing/vsync differ slightly from an exclusive run; no effect without the env var [WINDOWED].
* `NOTSA_STANDALONE_NOVSYNC=1` (env, off by default, run build only; opt-in for agent test runs): `RwCameraShowRaster` drops `rwRASTERFLIPWAITVSYNC`, i.e. Present uses sync interval 0 even when the game asks for vsync (menu "frame limiter" option, loading screens). The vsync-locked Present costs ~78 ms/frame on the dev PC (30-75 s cold starts); the game logic, `CTimer` and the software frame limiter are unchanged, only the display pacing differs (tearing possible in exclusive mode, DWM-composed in windowed mode). Frame-time measurements must not use it [INFRA-FAST].
* **Mouse / window / DPI (PLAYTEST-1 U1-U3, 2026-10-18)**: the exe reads the mouse through DirectInput (exclusive/relative in game) and re-centres the hidden Windows cursor every frame (`CentreMousePointer`); the SDL port has no DirectInput, so the run build puts the SDL window into **relative mouse mode** (raw unbounded deltas, cursor hidden and confined while the window has the focus; `UIRenderer` ctor), and `psMouseSetPos` also warps the SDL position and sets `m_nMousePosWinX/Y` (the exe got both from the WM_MOUSEMOVE of `SetCursorPos`). The process is per-monitor DPI aware here (the Windows compatibility layer `HIGHDPIAWARE` that every run dir of this PC carries, `HKCU\...\AppCompatFlags\Layers`; a `SetProcessDPIAware`/SDL hint cannot change it), so an exclusive mode switch that changes the monitor DPI (4K @150% -> 800x600) rescaled the 800x600 game window to 533x400 (800 * 96/144) and librw then reset the exclusive device to that size (game in a corner of the desktop, U1): the exclusive device now keeps its mode size and the window is re-fitted to it (exe `_rwD3D9CameraBeginUpdate` 0x7F78FD..0x7F798B only takes the client size for a windowed device). `SetVideoMode` delivers the `rsCAMERASIZE` the exe's synchronous WM_SIZE (sent inside `RwD3D9ChangeVideoMode` 0x7F8640) triggers, which SDL only queues. The exclusive device keeps its mode size when the window client size differs (exe 0x7F78FD..0x7F798B resets with unchanged parameters; librw used the client size). [PT-RENDER]
* `TRACY_ENABLE` undefined in the run build (events were queued with no server -> OOM) [S5].
* **Process image / ASLR (F3, 2026-10-17)**: the original `gta_sa.exe` is a non-relocatable image at the fixed base 0x400000 (no `/DYNAMICBASE`); the run exe has no data image, no placeholder and no fixed
  address any more: it is linked with the default base, `/DYNAMICBASE` and a relocation table, so the loader may place it anywhere (the base is logged as `image base 0x...` at the top of `standalone.log`).
  Consequences: code/data addresses differ per run (only `.map` offsets are stable), and the heap/stack layout is randomised by Windows for ASLR-opted-in processes where the original's was not. Nothing in the game logic is
  known to depend on absolute addresses (the census over the 6-minute route touches 0 bytes of the original image; address-keyed ordering of game objects does not exist: pools are index based), but a
  pointer-order or uninitialised-memory dependent behaviour of the ORIGINAL (heap garbage read by a bug) now reproduces less deterministically. For bit-reproducible debugging configure with `-DGTASA_ASLR=OFF` (`/DYNAMICBASE:NO`; the base stays the MSVC default 0x400000).
  The original-image diagnostics (census/poison, `StandaloneDetached`) still use the fixed layout `/BASE:0x400000 /FIXED` + the 9.1 MB placeholder; the code range there is `PAGE_NOACCESS` and any execution of an original
  address is a logged fatal [P2A, F3].
* **No original exe anywhere (G1, 2026-10-17)**: `StandaloneRelease` / `StandaloneRW` configure, build and run with no `gta_sa.exe` on the disk view (no CMake variable, no extraction step, no files next to the exe). The behavioural reference stays the original Win32 x86 build, but it is consulted only by the dev configurations: the exe-oracle tests (`tools/standalone/run_all_tests.sh`; without the exe they are `SKIP(no_exe)`) and `StandaloneDetached` (`GTASA_ORACLE_EXE`). Fidelity statements in this file that cite an oracle result were measured with the exe present.
* Hooks not ported or unverifiable: `CTaskSimpleChat` dtor 0x5F7FD0 is the base dtor jump; residual float oracle diffs: NaN payload/sNaN quieting only, `acos(-1)` is environment dependent [P2E, S2].
* Open oracle mismatches: `CCurves::CalcCurvePoint` (97%), `CWeapon::FireM16_1stPerson` `_ftol` + double 0.0125; `cHandlingDataMgr`/`ConvertDataToGameUnits` unproven (runtime-initialised constants) [S2 reciprocal audit].
