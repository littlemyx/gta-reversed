## U3 - mouse not captured: FIXED, reproduced + verified
* Original: DirectInput mouse (exclusive in game) + hidden Windows cursor (WM_SETCURSOR) + CentreMousePointer every frame -> unbounded deltas, no cursor.
* Root cause: the SDL port's mouse deltas come from SDL motion events; the run build's UIRenderer stub (`NOTSA_STANDALONE_RUN`) explicitly skipped `SDL_SetWindowRelativeMouseMode`, so the real cursor moved in absolute desktop coordinates, hit the screen edge (xrel 0) and the camera stopped; the cursor was visible in game (photos 2/4).
* Fix: relative mouse mode enabled in that stub (UIRenderer.cpp); `psMouseSetPos` (CentreMousePointer) also warps the SDL position and sets `m_nMousePosWinX/Y` (the exe got these from the WM_MOUSEMOVE 0x748323 of SetCursorPos, which SDL relative mode ignores).
* Repro/verification: windowed 960x600 with focus, real `mouse_event` sweeps (150 x 30 raw px, twice, the second without re-centring) with screenshots between: user exe: sweep 1 -> 69.8% of pixels changed, sweep 2 (cursor at the screen edge) 0.5-1.0%; fixed exe: sweep 2 72.6%, the hidden cursor stays at the window centre (1280,776 before and after).
* Not verified: menu cursor feel after CentreMousePointer (small code path, not looked at on screen); exclusive fullscreen mouse (same SDL path).

## U2 - dark/blue squares: FIXED, reproduced + verified
* Which pass: the HEAT HAZE post effect (`CPostEffects::HeatHazeFX`, active from game hour 10 = the user's photo 3 at 10:17; 180 random patches copied from the post-effects front buffer). The squares are patches copied from an UNINITIALISED front-buffer texture, drawn with alpha ~80.
* Root cause: in the exe `RwD3D9ChangeVideoMode` (0x7F8640) resizes the window with SetWindowPos; the WM_SIZE is SENT to `__MainWndProc` (0x747F04) and runs synchronously: rsCAMERASIZE -> `CameraSize` resizes the camera raster, then `SetVideoMode` (0x745C70) calls `SetupBackBufferVertex` (front buffer = pow2 of the camera raster) and reads `RsGlobal.maximum*` back. SDL only queues SDL_EVENT_WINDOW_RESIZED (nothing consumes it), so after a LIVE mode change (the user switched 800x600 -> 720x576 -> 640x480 -> 1440x900 -> 3840x2160 from the in-game pause menu, log 22:39-22:40) the camera raster was still the old size and the front buffer one mode step behind (1024x1024 for 1600x900, 2048x1024 for 2560x1440). `RwRasterRenderFast`'s StretchRect into it failed every frame (D3DERR_INVALIDCALL 0x8876086C, seen with a temporary diag), the copy stayed black. A fresh start in the same mode is fine (4K fmt 35 via NOTSA_STANDALONE_VIDEOMODE=51, game time up to 10:5x: no squares, StretchRect hr=0).
* Not a regression of stream D / FIX-AUDIT: the SDL standalone never delivered this resize, so no bisect was needed.
* Fix: `SetVideoMode` (VideoMode.cpp) runs the WM_SIZE body (rsCAMERASIZE with the client rect) after `RwD3D9ChangeVideoMode` under NOTSA_USE_SDL3. New injector command `vmode:<idx>` (menu resolution change) for regression runs (docs/STANDALONE.md).
* Verification: windowed route 960x600 -> 1600x900 -> 2560x1440, screenshot at ~10:50 game time: before, squares over the top-left half of the screen, same look as photos 3/4; after (diag build, and the committed code with the `vmode:` route): none; diag: front raster 2048x1024 / 4096x2048, 0 StretchRect failures.
* Left as in the exe: `HeatHazeFXInit` returns early when the type did not change, so patch sizes/positions stay those of the first mode after a live switch (the exe has the same early return).
* Ghost/double images of peds in photo 4: not reproduced separately; same post-effect family (copies of the front buffer), most likely the same cause; could also be the photo of the screen.

## U1 - first start, game in part of the screen: PARTLY verified
* Mode choice is the exe's: no gta_sa.set -> `CheckDefaultVideoModeSupported` takes the first 800x600x32 exclusive mode (index 4; VMODE.md asm). The original exe on this PC does the same (window 0,0,800,600 on an 800x600 display, run `orig_800`), so the "odd resolution" is original behaviour (the native-resolution default is a FIX_BUGS thing, off in the run build).
* "Not fullscreen": reproduced with the user's exe at 4K @150% (intro videos on): game window `winrect 0,0,533,400` (= 800*96/144) on the 800x600 display, the desktop visible around it - exactly photo 2. The exclusive switch moved the monitor to 800x600 @100%; the process is per-monitor DPI aware (a compat layer HIGHDPIAWARE sits on every run dir; `SetProcessDPIAware` and an SDL hint cannot change it - logged: awareness is already 2 at NOTSA_WinMain entry), so Windows rescaled the window, and librw's beginUpdate then Reset the EXCLUSIVE device to the 533x400 client size (the exe's `_rwD3D9CameraBeginUpdate` 0x7F78FD..0x7F798B takes the client size only for a windowed device, `cmp [0xC9C060]` at 0x7F796F).
* Fix: `WrappedBeginUpdate` (standalone/rw/platform.cpp) re-fits an exclusive device's window to the mode size, else hides the mismatch from librw for that call.
* NOT verified: the desktop scaling changed after ~00:40 (system DPI now 96), so the 533x400 shrink could not be reproduced again; the fix was only exercised as a no-regression check (exclusive 800x600 run with a forced SetWindowPos shrink: window returns to / stays 800x600; D3D9 also fights a manual shrink by itself). I did not change the user's display scale (system setting). Please re-test the first start on the 4K @150% desktop; if it still shows a corner window, the next step is handling WM_DPICHANGED (SDL message hook) to keep the exclusive window at the mode size.
* Side note: the desktop was seen at 2560x1600 (not 3840x2160) in runs after 00:57 - left by another agent's fullscreen run or changed by the user.
