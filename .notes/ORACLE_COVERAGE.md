# Exe-oracle coverage map

Generated by `tools/standalone/oracle_coverage.py` (inventory of every `RH_Scoped*Install` site + static analysis of the original exe). Re-run it after adding oracle rows.

* **9248** ported functions (hook sites with an exe address); **4658** covered by an exe-oracle row (address literal in `tests/standalone/*`).
* The uncovered rest is classified by the exe function's call closure: **A** pure (arguments + `this` memory only), **B** touches exe globals only, **C** indirect (vtable) calls, **S** reaches only allocator / CRT-lock / TLS imports (oracle-able since ORACLE-W2: `tests/standalone/oracle_alloc.h`), **D** reaches another Win32/D3D/CRT import.
  A is easy (random objects, bit-exact compare), B medium (both sides share the statics at the exe addresses, snapshot/restore), C medium-hard (fake vtables with recording stubs), S like A/B/C once the exe's CRT heap / locks are redirected to the shared deterministic arena (`oracle::alloc::InstallExe`, rows via `w2::BothA`), D not oracle-able as is (the import table is not populated; `oracle::Patch` can replace single callees such as rand / malloc).
* Script command handlers are covered by opcode in the `script_oracle_*` tests, not by address: their sites appear as uncovered here when the handler itself is not listed in a table with its address.
