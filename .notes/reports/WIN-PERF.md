# WIN-PERF - cold start, soaks, native frame times (Windows host, 2026-10-17)

Host: Windows 11, Ryzen 7 7700X, RTX 4080 (only D3D9 adapter), desktop 2560x1600@60 (it was 3840x2160 earlier in the day). Build: `build/StandaloneRelease` (exe relinked 08:38 by another agent from the shared tree, tip ~855dc7a3; my tools/injector commits 27b1edcd, 40c660d2). Full frame-time tables: `.notes/reports/WIN_FPS.md`.

## Verdict
1. **The ~95 s cold start and the constant 12.7 fps are NOT port bugs and not file access / Defender / shader assembly: they are the display's vsync pacing.** The process needs **1.8 s** from start to the first menu frame when vsync pacing is removed; everything else is `Present` waiting. The original exe shows the identical 78.5 ms frames and 48 s splash phase.
2. **Soaks: RESULT OK** (3 min and 15 min, both 21/21 markers, 0 errors, 0 `game [error]` lines, ~30 fps in every phase, quit via the pause menu works, process exits cleanly).
3. **Frame times (native):** ours holds the 30 fps cap as well as the original and uses 35-50 % less CPU per frame; no Wine-style walking gap. One port-only effect: ~50 ms streaming frame right after the new-game spawn. Found a **real behavioural difference**: the exe has an unconditional 14 ms busy-wait frame lock in `Idle()` that the port omits (uncapped ours 270-580 fps vs original ~125 fps; with the limiter off the port's new-game intro stalls at >1000 fps).

## 1. Cold start (task 1)
Measured with `tools/standalone/windows/startup_probe.py` (CreateProcess -> polls every 250 ms: process CPU, I/O, gstate `0xC8D4C0`, CTimer frame counter, log size) + the Present-log proxy `d3d9px`; stack samples with x86 cdb (`~*k`).

| run (ours, StandaloneRelease) | log.log first line | gstate 1 (splashes done) | gstate 7 (frontend) | first menu frame | process CPU at the end |
|---|---|---|---|---|---|
| exclusive 800x600 (set file / default of the exe), 2 runs | 0.4-0.5 s | 48.5 / 48.1 s | 52.5 / 52.1 s | **72.0 / 71.9 s** | 2.9 / 2.3 s |
| windowed 960x600 (`NOTSA_STANDALONE_WINDOWED`, the soak.sh default now), 2 runs | 0.3-0.5 s | 19.3 s | 21.2 / 21.1 s | **29.0 / 28.8 s** | 1.1 s |
| exclusive 800x600 with vsync neutralised by the proxy (`D3D9PX_NOVSYNC=1`) | 0.3 s | 1.3 s | 1.8 s | **1.8 s** | 9.7 s (busy frames) |
| original exe, exclusive (stub dpnhpast.dll, see WIN_FPS.md) | - | 48.1 s | - | frames 78.1-78.7 ms from the first splash frame | - |

Where the time goes (ours, exclusive): 0.0-1.0 s hooks + data image + fixups (InjectedHooksMain 30 ms; 0.77 s CPU in the first 5 s; I/O only 10 MB of reads, nothing is waiting on files - process I/O counters and the CPU trace are flat), 1.0-48.5 s two logo splashes. They are frame-count loops, not timers: `CLoadingScreen::DoPCTitleFadeIn/Out` (`source/game_sa/LoadingScreen.cpp:292,336`) draw 51 + 250 frames per logo (EAX, NVIDIA = 602 Presents, + more for the title) with `rwRASTERFLIPWAITVSYNC` (`psCameraShowRaster`: vsync while `CLoadingScreen::IsActive()`), so the duration is (frames x vsync period); cdb samples at 12/25 s: main thread in `DoPCTitleFadeOut -> DisplayPCScreen -> RwCameraShowRaster / Im2DDraw` (inside d3d9.dll waiting), CPU ~0.05 core. 48.5-52 s: data load (gxt/handling/popcycle/timecyc, log timestamps; 2.5 s of CPU), 52-72 s: another ~240 frames of loading-screen/fade before the menu goes active (`inputdrv until:menu` ok after 18 s).
* **vsync period measured in a bare D3D9 program** (`tools/standalone/windows/present_probe.c`, clear+Present only): exclusive fullscreen with PresentationInterval ONE = **78 ms for every mode** (640x480@59 ... 2560x1600@60; X8R8G8B8/A8R8G8B8/A2R10G10B10, refresh rate default or 60), windowed ONE = **30.4 ms**, IMMEDIATE = 0.06 ms (14 000 fps). DWM reports 60.0 Hz. So the driver/compositor, not the game, paces vsync-locked Present at ~12.7 Hz (exclusive) / ~33 Hz (windowed) on this PC today. The earlier 3840x2160 session had 52-60 fps menus; the 2560x1600 session (and now) does not. Not analysed further (no system/driver settings touched): suspects are the NVIDIA per-app/global "Max Frame Rate"/"Vertical sync"/"Low Latency" setting, a VRR/G-SYNC monitor behaviour, or the Meta Virtual Monitor / VR software that enumerates 7 virtual displays. **Suggest to the user:** check NVIDIA Control Panel -> Manage 3D settings (Max Frame Rate, Vertical sync, Low Latency Mode, Power management) and monitor VRR; try other refresh rates in the desktop mode.
* **The 12.7 fps of the earlier invalid soaks** (WIN-TEST soak3b/3d/3f: constant 12.7 fps from the first menu frame, misfiring click route) = exactly this: exclusive mode (default video mode on those runs) with limiter ON (= vsync) -> 78.5 ms per frame; the fixed `wait:20000` before the first menu click then fired ~50 s before the menu existed. Fixes: (a) the soak is windowed now (WINDOWED agent: `soak.sh` exports `NOTSA_STANDALONE_WINDOWED=960x600`) = 30 fps; (b) **40c660d2**: injector gate `until:menu` (+ soak route uses it instead of 20 s), so the route survives slow start-ups on any host. Windowed ONE vsync = 30.4 ms is why the windowed game still reaches its 30 fps limit.
* Not environment / not found: Defender or file-access stalls (none: flat I/O and CPU), shader assembly (skin VS now assembles with flags 2: no rejections, below), data image load (0.8 s), video skip (`NOTSA_STANDALONE_SKIP_VIDEOS=1`), streaming.
* `getenv("NOTSA_STANDALONE_...")` is called per Present in `ShimDumpBackBuffer` (cdb sample at 12 s: `common_getenv_nolock` on top): harmless at 12 fps but a few hundred ns x 1000 fps; could be cached (not changed, not in my zone).

## Honest caveats / what I did not do
* The `foreground` of the PC was taken by a Windows toast once; two early runs aborted by the guard in `inputdrv.exe` (it refuses to send keys unless the game owns the foreground). My own ShowWindow/BringWindowToTop focus attempt (removed again) put ours in a device-lost state once (no Presents for the rest of that run) - not a game finding.
* Early diagnostic runs of the ORIGINAL (before the silent proxy existed) were not guaranteed silent (it has no mute switch): the hang at `LoadLibrary` produced no audio, one run reached the intro movie phase for ~30 s. Later runs: dsound proxy + volume 0 + radio off + empty movies dir; the proxy's `dsmute.log` could not be collected (written at process detach, process is killed).
* Other agents' game runs and builds shared the PC (GPU lock serialised games, not CPU); the exe used by the 15-min soak was relinked by another agent at 08:38 (tip ~855dc7a3, includes WINDOWED's work). `/c/gta-perf` holds all raw data (runs/, *.bin Present logs, results.csv); not committed.
* The user's real `Documents\GTA San Andreas User Files\gta_sa.set` was replaced during runs and deleted afterwards (same policy as soak.sh; a pre-existing copy was backed up as `gta_sa.set.soak-bak` by D-B07V/WIN-TEST earlier).
