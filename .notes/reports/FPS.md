# FPS / frame pacing: environment (Wine + Rosetta + wined3d) vs port — agent FPS, 2026-10-10/11

Repo reverse/interior_c (tip during runs e32ff891..32409141), exe under test: `build/StandaloneRelease/bin/gta_reversed.exe` (18:24 build, copy in the private data dir), reference: `gta_sa_compact.exe` (copied as `gta_sa.exe` into a private data dir). Same private Wine prefix (clone of `~/.wine-msvc`), same data (symlinks to the Steam install), same video mode (index 1 = 960x600 windowed, forced through `gta_sa.set` for the original and by default in ours), `NOTSA_STANDALONE_SAMPLER` unset, no thread suspension anywhere. Full table of every valid run: `.notes/reports/FPS_table.md`; tools: `.notes/reports/FPS_tools/` (nothing committed, no source change left in the repo).

## Verdict (short)
1. **The stutter is overwhelmingly the environment.** Under the same host contention the ORIGINAL exe shows the same hitch storm: p95 54–256 ms, 10–60 frames/min over 100 ms, 60–500 frames/min over 50 ms, fps 19–25 with the limiter on (rows r303, r306, r412, r414). The host was saturated the whole time (parallel `cl.exe` builds of other agents, 18 cores, load average 12–25, CPU idle 7–35 %).
2. **The game costs ~55–65 ms of CPU per frame in BOTH exes** (original 54–68 ms/frame, ours 50–78 ms/frame; ~1.3–1.5 cores busy; ~700–900 draw calls per frame through wined3d). Frame cost is not a property of our port but of x87 code under Rosetta + wined3d draw/lock sync; at 30 fps that is ~2 cores, so any CPU contention turns into hitches. Wine's main-thread time inside D3D alone is 13–17 ms/frame in both.
3. **On a quiet host ours is smooth**: r206 (host idle 68 %) 30.0 fps, p99 39.7 ms, max 44 ms, 0 hitches in 30 s; r413 (idle 61–66 %) 28.0–28.7 fps, p99 43 ms, 0 hitches/min in the walking scenes. The 17–27 fps / stutter the user sees appears as soon as host idle falls below ~30 %.
4. **Port-only differences found (smaller than the environment effect):** (a) while WALKING ours uses ~+25–30 % more CPU per frame than the original (70–78 vs 56–68 ms; r302/r304/r305/r307/r411 vs r301/r303/r306/r412/r414) and so loses ~20–25 % fps under contention (walk_a 17–20 fps vs 20–24); standing still is equal (52–64 vs 54–66 ms). Not attributed (see "Not done"). (b) the cheat car (`JQNTDMH`) did not spawn within range in ours in ~7 of 8 runs although the cheat string was accepted (the original got in a car in 3 of ~8 runs; the typing check itself was flaky in both) — possible port bug, not investigated. (c) first-use stalls: even on the quiet host ours has ~10 frames >50 ms in the first 30 s of gameplay (mean 173 ms, 133 ms of it blocked inside D3D `Draw*` = wined3d first-use shader/texture work), none afterwards.

## Method
* Frame time = interval between `IDirect3DDevice9::Present` calls, logged inside the game process by a tiny proxy `d3d9.dll` (native-first override `WINEDLLOVERRIDES=d3d9=n,b`, identical for both exes), QPC timestamps, no polling. The proxy also (second version, runs r41x) time-stamps every call into wined3d per frame: Present, Clear, Draw*, resource create, Lock/Unlock, UpdateTexture/StretchRect (buckets below).
* Input and gating by an external `SendInput` + `ReadProcessMemory` driver (`sk3.exe`: menu/new game for the original; ours uses its built-in injector for the same menu path, then the same script for both): menu 15 s, foot_stand 30 s (after control + 2.5 s stable), walk_a/walk_b 20 s (W held). Scene valid only when gstate=9, menu=0.
* Limiter ON = `m_bPrefsFrameLimiter` 1 (30 fps cap in ours; the original's limiter settles at ~26 fps), OFF = 0, patched into `gta_sa.set` before each run. Interleaved O/R/R/O order; per scene I log the macOS `top` CPU idle % and load average at the same wall clock (`hostload.log`, `.cpu`), plus game-process CPU time from `ps` (cumulative cputime of the Rosetta process).
* Tools' own cost: a host logger (`top -l 2` every 3 s, `ps` 1/s) runs during every run; the same for both exes.

Reading: in both exes 40–70 % of every hitch frame is the main thread BLOCKED inside wined3d, waiting for its command-stream thread (ours: inside `DrawIndexedPrimitiveUP`/`DrawPrimitiveUP` — the Im3D/UP path; original: inside `VertexBuffer::Lock` on its dynamic VB ring), the rest is game-side time (descheduled threads under load, streaming, audio service, limiter busy-wait). The known Im3D-UP suspect costs ours ~16–18 ms/frame inside Draw vs ~12–15 ms inside Lock for the original: ours is +2–4 ms/frame in D3D, i.e. ~8 % of the frame, not the cause of the pacing. (An earlier Im3D dynamic-VB-ring experiment in this repo already measured 22 vs 24 fps and was rejected.) Hitches are bursty, not periodic: gaps between hitch clusters are 0.5–1.5 s with no fixed period in either exe (histogram in `attrib.py` output); the 0.5 s bin is a clustering artefact of the host load, not a timer.
Per-subsystem attribution INSIDE the game thread (CStreaming/CdStreamSync/LoadAllRequestedModels, ConvertBufferToObject, TXD read, RasterUnlock, Audio.Service, CGame::Process) was NOT measured: the patch kit (`FrameProf.h` + `apply.py`, QPC scopes, log of every frame >50 ms to `fprof.log`) is ready in `.notes/reports/FPS_tools/` but the build was refused: at 23:14 the shared tree had another agent's compile error (`CarCtrl.cpp:2481 nodeLow1 undeclared`) and a dirty `camera.cpp`; I reverted my edits (repo clean of them, build.lock released). Logging/file writes are negligible (standalone.log 118 lines, log.log 154 lines per run, no per-frame flush). wined3d first-use shader compile was not isolated; quiet-host data (r413) shows 133 ms blocked in Draw for the first hitches, then none.

## Sound
User's hypothesis (sound stutters because of the frame stutters) is consistent with the data: the audio service runs once per frame from `Idle()`, so a 100–300 ms hitch is a 100–300 ms audio gap in BOTH exes. Not measured directly: the order to run silent removed the audio recording part; with a Wine audio device present I did not collect `WINEDEBUG=warn+dsound` underrun counts (wine's dsound prints "Probable buffer underrun" / "audio glitch: dsound buffer too small for data"; ready to count on request). Classification: **environment (both exes)** for hitch-induced sound stutter; no port-only audio symptom was observed or tested.

## Shadows (screenshots through the proxy, `shot.req`)
Captured 3 consecutive frames each for day foot, day cars, car cameras, night (ours only: `NIGHTPROWLER` worked in ours, failed to register in the original run) — limited value: the spawn point is a narrow shaded alley (no sun, no cast ped shadow in either exe), no car came into view (cheat-car failure above), the 3-frame diffs mix camera movement/time of day (ours was still in the post-intro camera/tutorial state: diff 2–3 grey levels over the whole picture; original at rest: 0.1). No z-fighting, black or flipped shadow was visible in the captured frames of either exe; **no shadow glitch could be reproduced or classified** with these scenes. A proper test needs a sunlit street with a parked car and a streetlight at night (needs a reliable vehicle spawn).

## Environment misbehaviour of the exes (noted per the silent-run order)
* Wine audio driver disabled (`HKCU\Software\Wine\Drivers Audio=""` in the private prefix): the ORIGINAL dies at start (Unhandled page fault read 0x2DC1 at 0x7BF21239 in the main thread), OURS never leaves GAME_STATE_INITIAL (dsound: `GetDefaultAudioEndpoint failed 80070490`, `DirectSoundDevice_Initialize invalid parameter`). Both are unusable without an audio device. Workaround used for ALL runs after the order: audio driver left enabled but SFX and radio volume set to 0 in `gta_sa.set` (runs r201–r414); first set r1–r5 ran before the order with default volumes. The silent runs show equal frame timing to the earlier audible ones.
* The ORIGINAL freezes under Wine in some runs: (1) polling the game with `ReadProcessMemory` at 1 kHz froze the process at the start of gameplay in 2 of 2 runs (observer effect, never poll that fast); (2) with polling only every 250 ms it still hung at LOADING (gstate 8, frame counter constant) in 3 of ~14 runs (limiter off 2x, limiter on 1x); (3) wined3d `Direct3DCreate9` startup flake (about half of starts) affected both exes. Ours did not hang.
