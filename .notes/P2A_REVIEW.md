## Findings by severity

### S1 (critical) - the code-pointer classifier rewrites ~4,400 dwords that are NOT pointers (strings, UTF-16, u16-pair struct data)   [item 5]
`extract_exe_data.py:116-137` (classification) and `Fixups.cpp:198-208,218-241` (the runtime re-classification, the one that actually writes) accept ANY dword in [0x401000,0x858000) that has a code neighbour (V) or is not "text-like" (C). Real function entries are 16-aligned (99.9% of symbols), the data is not:
| class | not 16-aligned | examples |
|---|---|---|
| C, target in game code (<0x820000) | 349 | `0x8611B0 = 0x00770001`, `0x861360 = 0x00780005` (u16 pairs inside a struct array of floats `3F800000 3F879C7D ...`, i.e. real tuning data), `0x85F6CC = 0x00812CDE` (random table) |
| C, target 0x820000+ (CRT/RW range) | 1,889 | `0x8611D4 = 0x00840008`, `0x8627E8 = 0x0082000A` (same struct arrays) |
| V runs, game range | 2,138 | `0x8598D4..` = `GAN\0 WIT\0 NLG\0` (3-char ASCII strings: the text filter is applied ONLY to isolated dwords, run >= 2 bypasses it), `0x85FCF0 = 0x00520044 0x0048004D ...` (UTF-16 strings) |
| V runs, CRT range | 233 | mostly `0x82263A` = `_purecall` (legit, keep) |
In addition aligned look-alikes `0x00NN0000` (u16 pair {0,NN}) : 122 C dwords, two of which collide with real hooked functions (`0x860E2C = 0x004F0000` = `CAESoundManager::Service`, `0x8A2A18 = 0x004D0000` = `CAnimBlendNode::GetEndTranslationCompressed`) -> data is overwritten with OUR function pointer, not just a trap stub. Expected random aligned hits for ints/hashes: ~1/16 of the unaligned count, so the unaligned rule below removes ~95% of the damage.
Opposite error: `TextLike()` (Fixups.cpp:96-100, extract:`text_like`) classifies ~12% of ALL 16-aligned code pointers as text (`0x425F70`, `0x463830`, `0x4E4150` have bytes `70 5F 42 00` = "p_B\0"): 39 of the 1,907 "S" dwords equal a known function start or a call target (about 5-10 are genuinely pointers, e.g. `0x85DA64 -> 0x425F70`, `0x867B68 -> 0x463830`); they stay raw exe addresses (see S2: below 0x5746D0 that is silent execution of OUR code at a wrong address).
FIX (both files, keep in sync): a dword is a code pointer only if
`(v & 0xF) == 0 && (v & 0xFFFF) != 0` OR `v` is in a known-function-start set (`FnMap` at runtime = hooked functions, plus symbols/call-target set emitted by the extractor as `code_starts.bin`: all `E8/E9 rel32` targets in .text + the 9,016 symbols). Apply the text filter ONLY to non-aligned values and to runs too; drop the "run >= 2 => V" shortcut for unaligned values. Add a self-check in `ApplyToDataImage`: changed dwords == FixedBySlot + FixedByFunction + Trapped. Expected: C 4,206 -> ~1,950; V 10,572 -> ~8,200 (unaligned V were mostly dead jump tables / strings / EH data; 69 jump-table-like runs are harmless either way).

### S2 (high) - the low 1.5 MB of the ORIGINAL code range is our own code, not NOACCESS   [new]

### S6 (medium) - `.rdata` stays writable   [item 4]
`DataImage.cpp:125` makes the whole [0x858000,0xCB0000) RW and nothing re-protects it. Consequence: a buggy port that writes through a `StaticRef` into .rdata (vtables, float constants, string tables) silently corrupts/masks bugs, and a vtable overwrite is never caught. Original sections: `.rdata` = [0x858000,0x8A4000) is the only read-only one (flags 0x40000040); `.data/_TEXT_HA/_rwdseg` are RW. Legit .rdata writers: none (the delta writer starts at 0x8A4000, `initterm_delta.py` line `i = 0x8a4000 - BASE`; only 12 `StaticRef` globals live in .rdata, all float/bool constants).
FIX: at the end of `ApplyToDataImage()` (after the pointer rewrite, `Fixups.cpp` before the final `Log`): `VirtualProtect((void*)0x858000, 0x8A4000-0x858000, PAGE_READONLY, &old)` with the range taken from `original_data.json` (`sections[].name==".rdata"`, add `rdata_lo/rdata_hi` to the json so nothing is hard-coded). First run with it on and treat any AV as a bug report (the VEH returns CONTINUE_SEARCH for non-fetch AVs; add an `Fatal` with address for writes into [DataBase,DataEnd)).

### S7 (low/medium) - `.CRT$XIB` ordering   [item 6]
Sound: UCRT/MSVC run `_initterm_e(__xi_a,__xi_z)` before `_initterm(__xc_a,__xc_z)`; `StaticRef` users (`static inline auto& x = StaticRef<T>(addr)` is a dynamic initializer: reinterpret_cast is not a constant expression, so no `constinit`/constant-init can run earlier) and `init_seg(lib)` (`PLUGIN_SOURCE_FILE`, Base.h:251 -> `.CRT$XCL`) are all in XC. The loader is CRT-free (verified). Residual risks: (a) `thread_local` with dynamic init (`General.h:22-23`, `std::random_device`/`mt19937`) is initialised via TLS callbacks `.CRT$XLx` which run BEFORE the CRT initializers - not touching the image, so safe, but any future thread_local that calls `StaticRef` would hit the `assert`; (b) `/include:_notsa_standalone_data_image_early_init` is the x86-decorated name, OK; on x64 it would be undecorated - irrelevant (x86 only); (c) the pad must already be mapped (it is, it is part of the image).

### S8 (low) - trap handler / threads   [item 7]
`AddVectoredExceptionHandler(1,..)` is process wide: audio streaming thread and any `CreateThread` thread are covered. `FnMap/SlotMap` are read-only after registration (function-local statics = thread safe init), `MakeStub` is mutex-protected, `s_logged` atomic, `Fatal` = `TerminateProcess` (no unwinding, safe from any thread), trap stub reads `[esp+4],[esp+8]` correctly for `__cdecl(uint32,uint32)`. Gaps: (a) `Resolve()` can create stubs at runtime from other threads while `g_Chunk` allocation is under the same mutex, OK, but stubs are RWX (`PAGE_EXECUTE_READWRITE`) - make them RX after writing; (b) the handler dereferences `*(uint32_t*)Esp` without `IsBadReadPtr`/SEH - a trap taken on a stack-overflow path double-faults silently; wrap in `__try`; (c) there is no `SetUnhandledExceptionFilter`/crash log for other AVs (e.g. a read of the NOACCESS range as DATA: `ExceptionInformation[0]==0` and `[1]` in [CodeLo,CodeHi) -> add a `Fatal("data access to original code range 0x%08X from 0x%08X")`).

### S9 (info, clean) - Unicorn replay delta   [item 8]
Covers exactly the C++ initialisers (`__xc_a..__xc_z` 0x8A4000..0x8A5A10, 1,667 entries); the 6 C initialisers (`__xi`, 0x8A5A14..0x8A5A30: `_onexit` table, stdio `__piob`, CPU flags, `_setmbcp`, unhandled-filter, lowio) and `_FPinit` are CRT-internal and correctly not replayed (our CRT replaces them; no source `StaticRef` touches 0xC99xxx-0xCA0xxx or 0x8E30xx-0x8E37xx CRT globals). Checked the final image: NO dword in the delta points into the emulator regions (stack 0x2000000, FS 0x3000000, sentinel 0x4000000, GDT 0x6000000; the only hit is `0xC0B0BC = 0x02020202`, bytes). Heap: the audit proves none of the 1,667 initialisers allocate (0 unmapped fetches), and every pointer the delta adds is either into the data range (static objects) or one of 13 text-like code-range dwords. `--no-initterm` would leave ~188 KB of constructed state (vtable pointers of ~100 static objects, 1,489 float constants) missing. atexit: the 140 recorded destructors belong to static objects (CColModel x14, CGarage[], CSprite2d x6, Fx_c/FxManager_c, CText, CMenuManager, CAudioEngine/CAEAudioHardware, CAEStreamTransformer, CLoadMonitor, CPlayerInfo, ...). None owns a file handle or an RW object that the game does not already shut down explicitly (`CGame::Shutdown`, `RsTerminate`, `CAudioEngine::Shutdown`, `CdStreamShutdown`); skipping them at exit is safe. Only visible effect: the audio thread/DirectSound is released by process teardown instead of CAEAudioHardware dtor - harmless. If a clean exit is wanted later, call `CAEAudioHardware::Terminate()` from the standalone exit path rather than replaying atexit.

### S10 (low) - misc
