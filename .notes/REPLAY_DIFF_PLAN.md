## 1. What exists (answers to Q1)
* **Original exe leg**: `tools/standalone/gameplay_regress/orig_run.sh` (71 lines) runs `C:/gta-perf/orig/gta_sa.exe` = a copy of repo-root `gta_sa_compact.exe` (v1.0 US, 5189632 bytes, identical size; `perf_datadir.sh orig` copies it; the Steam gta-sa.exe v3.0 is never used). Data = Steam links. Input = `inputdrv.exe` (SendInput scancodes, **real time**, foreground guard) from `gameplay_regress/orig/*.scn`; state = out-of-process poller `orig_gr_poll.py` / `cheat_probe_exe.py` (ReadProcessMemory, 0.5-1 s samples). Proxies already used in-process: `d3d9.dll` (Present log, NOVSYNC, screenshots) and `dsound.dll` (mute). The exe cannot be redirected: `docs_backup/docs_restore` of Documents\GTA San Andreas User Files, fullscreen exclusive (desktop mode switch), needs the foreground (a run aborts when another window has it - seen once in this task: `[ABORT] game window is not in the foreground`).
* **Gap**: sampled, real-time, 1 s granularity - useless for per-frame lockstep. Nothing in-process runs inside the original exe today.
* **In-process hook in the original: works** (probe): the exe imports `vorbisFile.dll` *statically* (7 functions; PE import table), so a proxy `vorbisFile.dll` (rd_orig.c; real DLL renamed `vorbisFile_real.dll`, 7 naked jmp stubs) has `DllMain` run before the exe entry point and can patch code with `jmp rel32` (whole-function replacement, no trampolines needed). d3d9/dsound are LoadLibrary'd late (not static imports) so they are too late for startup hooks. Hard-link caution: the data dir's `vorbisFile.dll` is a hard link into the Steam folder (45 links) - delete the *name* and copy, never write through it (rd_orig_run.sh does).
* **ASI/plugin build of this repo**: `source/CMakeLists.txt:152/210` still has the MODULE/`.asi` target and the oracle tests build with `NOTSA_ORACLE_ADDRESS_GLOBALS` (globals at original addresses); not built or verified in this task. It is the route for slice 2 (one C++ reader compiled against the game headers for both sides), the C proxy is enough for the first slices.
* **Port leg**: the run build has no fixed addresses any more (detached globals, F3) - `inputdrv.c`'s "same VAs" comment is stale; the port must trace from inside (C++ variables). Its input injector `NOTSA_STANDALONE_INPUT` (SDLWrapper.cpp InjPump, `GetTickCount64`-based) is real-time, not frame-based.
* **CReplay** (`Replay.cpp`) stores entity/camera packets of the last ~30 s, not input, and is not a deterministic re-simulation: not usable as the input record (its packet idea is a precedent for the state dump).

## 3. Input (Q3)
One recorded stream, applied **at the same logical point** in both exes: the tick (start of `CTimer::Update`, called at the top of `Idle`/`FrontendIdle` before `CPad::UpdatePads`, app_game.cpp:310/401-405). At the tick write `CPad::TempKeyState` (orig 0xB72CB0, CKeyboardState), `TempMouseControllerState` (0xB73404) and the pad `PCTempJoyState`; `UpdatePads` copies Temp -> New at its end (Pad.cpp:240), so an entry for tick N is consumed by frame N+1 on both sides (constant latency). The OS message pump runs before Idle, so real keystrokes are overwritten. File = text lines `frame keybitmap(hex) mousedx mousedy buttons padstate`; recorded either from the existing route injector (convert `NOTSA_STANDALONE_INPUT` events to frames by running the port once) or from the tick of a live session. First test (slice 3): hold W for 300 frames, compare the position trajectory.

## 4. State per frame (Q4)
Hash layers, all in one line so the first mismatching *layer* names the subsystem; the line is cheap (the probe hashes 269 KB of script space per frame at >100 fps):
1. frame: fc, CTimer ms (clipped), non-clipped ms, timestep bits, RNG seed, rand-call count since the last line, srand log of the frame.
2. player: position/heading/health/armour/wanted/weapon/pedstate, task chain types.
3. pools: per used slot of ped/vehicle/object/building-dummy pools: (slot, model, position bits, heading, health, state, flags) - one hash per pool + counts; first-mismatch slot index reported.
4. script: ScriptSpace globals hash (0xA49960, 269000 bytes), per running script (IP, wake time, locals hash).
5. camera (matrix, mode), clock/weather, wanted/crime lists, streaming (loaded-model bitset hash), population counts, audio stats off.
Mismatch handling: both sides support `LOCKSTEP_DUMP_FRAME=N` (full human-readable dump of all layers for frame N; reruns are deterministic once the pins hold) and `diff` prints the first differing layer/field/slot with both values. Float fields compare **bit-exact** (the port is /arch:IA32 bit-exact by design); the portable build uses a per-field tolerance table.
Probe format (what exists): `F fc tms rng ncalls px py pz hp peds vehs scripthash`, `S fc ra seed` per srand.

## 5. Design (components, code, builds)
* `source/standalone/lockstep/` (port + portable): `Lockstep.cpp` (arm point, tick, pins), `StateHash.cpp` (layers of section 4, **one source** written against the game headers), `InputReplay.cpp`. Compiled into the run build behind `NOTSA_LOCKSTEP_*` env (inert by default, listed in standalone_deviations.tsv like the other test switches).
* **Original-exe leg**: `tools/standalone/replay_diff/rd_orig` - a DLL (`vorbisFile.dll` proxy) built from (a) C hooks for rand/srand/timer/arm (probe, exists) and (b) later the *same* `StateHash.cpp` compiled with `NOTSA_ORACLE_ADDRESS_GLOBALS` (structs are layout-faithful, so `CWorld::Players[0].m_pPed` etc. read the original addresses): one reader for both sides, no schema duplication. x86 MSVC, built by `build_orig.sh` into `C:/gta-perf/rd`.
* **Runner**: `tools/standalone/replay_diff/run.sh <scenario>`: GPU lock, private data dirs for both exes, same `gta_sa.set` (seeded into the port's private USERDIR, written into Documents with backup/restore for the original, exactly as orig_run.sh), runs both legs sequentially, `rd_diff.py` report, exit code = frames equal threshold.
* **Portable build (Mac, portable/main)**: the harness is the source files above plus the text trace format; Windows produces a *golden trace* per scenario (original exe and Win32 port) stored as an artifact (not the exe); the portable run writes the same format and `rd_diff.py` compares it against the golden Win32-port trace (exact on integer fields, ulp tolerance on floats because x87 vs SSE) and, once Win32-port == original is established for a scenario, transitively against the original. No original exe is needed on the Mac. `GameRand.h`-style RNG ownership is required there too (it already is the design of the run build).
* Cost model: one scenario run per exe = menu/new-game (~60 s real) + N frames at ~100+ fps; the per-frame line is ~100 bytes -> 6000 frames = 0.6 MB.

## 6. Risks
1. Audio / script-audio coupling and threads (rows 6, 9) may force audio-off pinning (a deterministic stub of `CAEAudioHardware` completion) - the largest unknown.
2. Real-time loops that wait on the pinned clock (Idle lock solved; videos, loading min-times, DirectShow) - the pin is only active after the first CTimer::Initialise and the loading screen uses its own clock; keep the arm logic strict.
3. Both exes must start the same game: same save state (new game), same gta_sa.set bytes, same data; the original's prefs file is outside the sandbox (Documents) - always backup/restore.
4. A-A noise hides A-B findings: acceptance of every slice starts with A-A equality of each exe on its own.
5. Orig leg is fullscreen/foreground-bound (inputdrv foreground guard); the overnight loop and the user share the GPU lock; ~4 min per orig run.
6. The tracer must not alter the thing it measures: hooks replace the CRT rand and 4 functions; port-side calls are inside `#ifdef NOTSA_STANDALONE_RUN` and inert without the env var (Release run-build gate required before landing as part of slice 1).

## 7. Probe result (feasibility, Q5) - numbers
Setup: original gta_sa_compact.exe copy + `vorbisFile.dll` proxy (rd_orig.c) vs `gta_reversed.exe` (StandaloneRelease worktree build with Lockstep.cpp), same gta_sa.set, menu/new game by real-time input, trace from the first frame with a player ped (the intro cutscene starts there), 6000 frames per run, NO input after the new game. Minimal hash = fc, tms, rng, rand-call count, player pos (3 floats) + health, ped/vehicle pool counts, script-space hash.

| Pair (pins) | frames compared | equal prefix | equal frames | first mismatch |
|---|---|---|---|---|

What the numbers say: **timer pinning works** (tms advances exactly 16 per frame, no Idle hang); the dominant early divergence is the RNG state at the arm point (loading-screen frames consume a real-time number of rand calls) - hence pin bit 8 (re-seed at the arm point) and the arm-point design above; after that the next layers (population at frame 4, script at ~2500) are the real work of slices 2-3. With the arm re-seed, **frame 0 of orig and port is bit-identical** in player position/health, pool counts and the script-space hash (the new-game start state matches), and the first A-B difference is the RAND CALL COUNT of frame 1 (orig 74, port 327): the first concrete lead for slice 5. The A-A noise left (orig: 5 extra rand calls in frame 1 between two runs; port: 1 call at frame 11) is the audio/streaming/threads family of section 2 (rows 6-9). Also confirmed: the `srand` at the same logical frame has a different argument per run (`134c0d39` vs `134c2d39`: pointer-based, Entity.cpp:1056, row 8). Answer to Q5: yes, feasible - 6000 frames per run traced in-process on both exes with 4 hooks; not yet lockstep-equal beyond 1-11 frames, with a known list of causes. Raw probe traces: C:/gta-scratch/rdd/out (a*, b*, c*: orig; p*, q*: port).

## 8. Slices (each: one agent, <= 100 min, rules v4)
1. **RD-ARM**: finish the pins that the probe found: arm-point re-seed + fc normalisation (bit 8 + row 5) in rd_orig.c and Lockstep.cpp, the S-line source tag (file:line) in the port trace, `run.sh` runner (both legs, private dirs, lock, restore), CI-less. 3. **RD-INPUT**: frame-indexed input record/replay at the tick (section 3) for both exes + a recorder from the existing routes; acceptance: hold-W/turn/enter-vehicle scripted run, orig-vs-orig positions equal for every frame, trajectories non-trivial (CJ moves > 20 m).
4. **RD-STATE**: the layered hash + `LOCKSTEP_DUMP_FRAME` dump + first-mismatch report (section 4) with the single shared `StateHash.cpp` (ORACLE_ADDRESS_GLOBALS orig-side build); acceptance: layer table matches between the two legs on frame 0, unit test that a mutation of one ped field flips exactly its layer.

6. **RD-SCENARIOS**: 5-8 recorded scenarios (walk, drive, shoot a ped, wanted level + police chase, enter/leave interior, a mission start, save/load, weather/time passes), golden traces stored under `C:/gta-scratch/rd_golden` (+ manifest in `.notes`), hooked into `gameplay_regress.sh` as an optional `-l` lockstep pass; acceptance: a table "scenario: frames equal / first diverging layer".
7. **RD-PORTABLE**: Mac side: build Lockstep + InputReplay into portable/main, golden-trace comparison with float tolerance, documented in the portable README; acceptance: portable run of the intro scenario compared against the golden Win32-port trace with a per-field tolerance table and a pass/fail line.
8. (optional) **RD-BISECT**: `git bisect run` wrapper over the lockstep runner for a regression "equal until frame F" - a one-command answer to "which commit made frame F diverge".
