## Task 2: matrix list
### Facts established (exact, with the new env-gated checker NOTSA_MATRIX_CHECK=1)
* `NotsaCheckMatrixLists` (Placeable.cpp; called every frame after CWorld::Process and after the two CarCtrl link copies) walks list 1 / list 2 / free list: prev-next symmetry, links inside the array, total == 900, used link -> owner != null and owner->m_matrix == link, free link has no owner. First failure of the run is printed with frame number and details ("[matrix] CHECK FAILED ..."). `NotsaMatrixTrace` additionally prints, when an entity allocates a matrix while an older link still names it as owner, a backtrace of the allocation and of the allocation of the stale link.
* Reproduced on the unmodified-logic exe, natural (no forced fault): run r6 (stab_soak2 route, frame 4506, about 1 min after the new game) and soak s2 (frame 7482). In both a **list-1 link names a ped slot as owner while that ped's own m_matrix is a different link** (a ped constructed in a slot whose previous tenant left a list-1 link behind): `CPopulation::AddPed -> CCivilianPed ctor -> CPhysical ctor -> AllocateStaticMatrix` finds link #N (list 1) with owner == the new ped.
* Allocation stack of that stale link (s2, link #20; r6 similar): `CPlaceable::AllocateMatrix <- CPlaceable::GetMatrix <- CTheScripts::ClearSpaceForMissionEntity (entity->GetMatrix() of a colliding entity) <- CCarCtrl::CreateCarForScript <- PlayCmd roadveh`. So the link was created by the lazy `GetMatrix()` of an entity whose m_matrix was null, and it was never given back when that entity (a ped slot) went away. Peds get a list-2 (static) matrix in CPhysical::CPhysical, FreeStaticMatrix has no callers, so a ped with a null m_matrix (-> list 1) is itself the anomaly; the pool-slot tenant that owned link #20 was not destroyed through ~CPlaceable.
* In s2 the same ped slot (0x...eef0) was re-constructed by CPopulation::AddPed 6 times (frames 7482..8364) and every time link #20 (list 1, allocated by that `ClearSpaceForMissionEntity -> GetMatrix` call) still named the slot as owner: the slot's later tenants all released their own links correctly, #20 belongs to the tenant that existed when ClearSpaceForMissionEntity ran (an entity with a null m_matrix: either a ped that lost its static matrix or, most likely, a stale pointer in that function's `colEntities` snapshot to a ped that `CPopulation::RemovePed` had just deleted - the driver / passengers it removes are still in the 16 entry list). At frame 8464 the stale link reached the oldest position (free 0, list1 605, list2 295) and the guard fired once (`[matrix] ERROR ... guard FIRED #1`); in s1 and r1/r2/r3/r5/r7/r8 nothing happened.
* The matrix list is routinely full (free 0..477 depending on the area, list1 ~200-570 buildings/dummies lazily allocated, list2 ~200-320 statics); eviction of the oldest list-1 link is normal. The ownerless oldest link of STAB1 is the same stale-link family (owner dead / owner->m_matrix null), reached by the eviction.
### Fix landed
* `CMatrixLink::operator=` (portable): the implicit one also copied m_pOwner / m_pPrev / m_pNext. `CCarCtrl::CreateConvoy` (`*car->m_matrix = *vehicle->m_matrix`, CarCtrl.cpp:788) and `CreatePoliceChase` (:907, wanted-level police chases) do exactly that on CMatrixLink operands (the exe calls CMatrix::operator= 0x59BBC0: matrix only). Result: the car's link becomes a clone of the donor's (owner = donor, prev/next = donor's neighbours): both lists are spliced wrongly and the clone stays behind with a dead owner. Now copies the CMatrix part only. Proven only by reading (the two sites were not reached in the diagnosis runs: the checker's "site reached" print never fired in r1/r3), so it is a real latent bug but NOT shown to be the cause of the stale ped link above.
* The eviction guard (STAB1) now logs loudly: `[matrix] ERROR: ownerless / stale link reclaimed (guard FIRED #n)` on stderr (first 50), instead of a one-line spdlog warning.
### Not found
The path that leaves a list-1 link owned by a ped slot: a ped with a null m_matrix (ClearSpaceForMissionEntity's `entity->GetMatrix()` on a ped colliding with the new script car allocated it lazily) that is later removed without ~CPlaceable freeing that link. Next step for whoever continues: log in `CPlaceable::~CPlaceable` / `CPool::Delete` (ped pool) for slots whose link is still claimed, and in `AllocateMatrix` the entity type + whether `this` is inside the ped pool; the env-gated trace in Placeable.cpp already prints both stacks.
